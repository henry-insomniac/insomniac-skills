# Git 协作规范

## 分支策略

- 默认主分支为 `main`。
- 功能分支建议使用 `codex/<topic>`、`feat/<topic>` 或 `fix/<topic>`。
- 分支名使用小写短横线，例如 `codex/init-docs`、`feat/release-skill`。
- 不在同一分支混合无关目标。

## 提交规范

提交信息建议使用简洁英文或中文动词短语，格式保持一致：

```text
docs: 初始化 Agent 文档
feat: 添加发布说明 skill
fix: 修复诊断脚本路径解析
chore: 更新工具链配置
```

常用类型：

- `docs`：文档变更。
- `feat`：新增 skill、模板、脚本或能力。
- `fix`：修复 bug。
- `refactor`：不改变行为的结构调整。
- `test`：测试相关。
- `chore`：工具链、配置、维护性变更。

## 提交前检查

提交前至少确认：

- `git status --short` 中只包含本次任务相关文件。
- 新增文档可以从 `AGENTS.md` 或 `.claude/README.md` 找到入口。
- 修改 skill 后更新了相关规范或示例。
- 修复 bug 后更新了 `.claude/bug-fix-log.md`。
- 有可运行测试或验证命令时，已经执行并记录结果。

## Pull Request 规范

PR 描述建议包含：

- 背景：为什么需要这次变更。
- 变更：核心修改点。
- 验证：执行过的命令或人工检查。
- 风险：可能影响的流程、兼容性或后续工作。

## 代码评审重点

- skill 触发条件是否清晰。
- 流程是否可执行，是否有明确输入和输出。
- 是否引入了不必要依赖或过度抽象。
- 是否把个人环境、账号、密钥或临时路径写入仓库。
- 文档和实际目录结构是否一致。

## 禁止事项

- 不提交密钥、令牌、Cookie、账号凭据或私有数据。
- 不在未确认范围时执行破坏性 Git 命令。
- 不把无关格式化和业务变更混在一个提交里。
- 不依赖仅存在于个人机器上的绝对路径。
